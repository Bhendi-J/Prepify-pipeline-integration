# Prepify — phased build roadmap

A checklist version of the architecture we designed, broken into phases you can build and test independently. Each phase lists what's new, what to install (if anything), and what "done" looks like — so you can track progress here instead of scrolling back through chat.

## Phase 1 — Documents & ingestion skeleton ✅ done

**New models:** `Document` (`id`, `user_id`, `title`, `source_type`, `file_path` or `storage_key`, `status`, `uploaded_at`)

**New files:**
- `models/document.py`
- `schemas/document.py` (`DocumentCreate`, `DocumentRead` — with `status` so the client can poll)
- `repositories/document_repo.py`
- `api/v1/documents.py` — `POST /documents` (upload), `GET /documents/{id}`, `GET /documents`
- `workers/celery_app.py` — Celery instance + broker config
- `workers/tasks.py` — a `process_document(document_id)` task, skeleton only (just flips status to `processing` → `ready` for now, no real extraction yet)

**New infra:** Redis (broker for Celery) — either installed locally (`brew install redis`, same pattern as Postgres) or via Docker.

**New installs:** `celery`, `redis` (the Python client)

**Steps:**
1. `Document` model → Alembic migration → apply.
2. Upload endpoint: accept a file, save it somewhere (local disk path is fine for now — don't reach for S3 yet), write a `Document` row with `status="pending"`, enqueue the Celery task, return immediately.
3. Get Redis running locally, confirm Celery worker connects (`celery -A app.workers.celery_app worker --loglevel=info`).
4. Task skeleton: just updates `status` to `ready` after a `time.sleep()` stand-in — proves the whole async loop (API enqueues → worker picks up → DB gets updated) before any real logic exists.

**Definition of done (met):** upload a file via curl/HTTP, poll `GET /documents/{id}`, and watch status advance without the API blocking.

---

## Phase 2 — Chunking & embeddings ✅ done

**New models:** `Chunk` (`id`, `document_id`, `topic_id` nullable for now, `content`, `embedding vector(N)`, `token_count`)

**New files:**
- `models/chunk.py` (needs `pgvector.sqlalchemy.Vector`)
- `services/ingestion.py` — `extract_text()` (dispatch by file type: plain text first, PDF later), `chunk_text()`
- `services/llm_client.py` — thin wrapper around whichever provider you pick, one method for embeddings
- `repositories/chunk_repo.py` — bulk insert

**New infra:** `pgvector` Postgres extension (`CREATE EXTENSION IF NOT EXISTS vector` — first migration in this phase, before the `Chunk` table migration)

**New installs:** `pgvector` (Python package), `huggingface_hub`, `numpy`; `pypdf` or similar once you go past plain text

**Steps:**
1. Enable the extension migration first — separate migration file, applied before the `chunks` table migration.
2. Start with plain `.txt` uploads only — don't solve PDF/DOCX extraction and chunking strategy in the same step.
3. Wire the real `process_document` task: extract → chunk → call `llm_client` for embeddings → bulk insert into `chunks`.
4. Manually verify with a raw SQL query that embeddings actually landed (`SELECT id, content, embedding IS NOT NULL FROM chunks LIMIT 5`).

**Definition of done (met):** upload a plain-text file, and within a few seconds `chunks` rows exist for it with non-null Hugging Face embeddings.

## Phase 3 — Topics & retrieval ✅ done

**New models:** `Topic` (`id`, `user_id`, `name`, `parent_id` nullable — self-referencing for hierarchy)

**New files:**
- `models/topic.py`
- `schemas/topic.py`
- `repositories/topic_repo.py`
- `api/v1/topics.py` — basic CRUD
- `services/retrieval.py` — `embed_query(text)`, `similarity_search(topic_id, query, k)` using pgvector's `<->` operator

**Steps:**
1. Topics CRUD first, independent of everything else — lets you tag documents/chunks to a topic.
2. Backfill: when uploading a document, let the user assign it to a topic (or infer later — don't automate this yet).
3. `similarity_search`: given a query string, embed it, run a `chunks.embedding <-> query_embedding` ORDER BY, scoped to `topic_id`, return top-k chunks.
4. Test with a raw script or a temporary debug endpoint, not yet wired into question generation.

**Definition of done (met):** given a topic and a plain-English query, you get back the k most relevant chunks from your own uploaded material.

## Phase 4 — Question generation

**New models:** `Question` (`id`, `topic_id`, `chunk_id`, `question_text`, `answer_text`, `difficulty`)

**New files:**
- `models/question.py`, `schemas/question.py`
- `services/question_gen.py` — `build_prompt(chunks)`, `generate_question()`
- `repositories/question_repo.py`
- `api/v1/practice.py` — `POST /practice/{topic_id}/question`

**Steps:**
1. Retrieve top chunks for the topic (Phase 3's function), build a prompt, call the LLM synchronously (this path is fine to keep sync — it's a handful of chunks, fast enough not to need a Celery job).
2. Store the generated question so it can be reused rather than regenerated every time (cheaper, and needed for the next phase to reference `question_id`).
3. Return the question (not the answer) to the client.

**Definition of done:** hitting the practice endpoint for a topic you've uploaded material for returns a real, relevant question.

## Phase 5 — Attempts & the adaptive engine

**New models:**
- `Attempt` (`id`, `user_id`, `question_id`, `is_correct`, `response_time_ms`, `created_at`)
- `Mastery` (`user_id`, `topic_id`, `ease_factor`, `interval_days`, `next_review_at`, `streak`)

**New files:**
- `models/attempt.py`, `models/mastery.py`
- `services/adaptive_engine.py` — `sm2_update(mastery_row, was_correct) -> Mastery` — a pure function, no DB/HTTP inside it, so it's trivially unit-testable
- `repositories/attempt_repo.py`, `repositories/mastery_repo.py`
- `api/v1/practice.py` — add `POST /practice/{question_id}/attempt`
- `api/v1/progress.py` — `GET /progress/due` (what's due for review), `GET /progress/{topic_id}`

**Steps:**
1. Submitting an attempt writes the `Attempt` row and reveals `is_correct` + the stored `answer_text`.
2. Same call feeds `sm2_update()` — write the unit test for this function *before* wiring it into the route, since it's pure logic with no infra dependency.
3. `GET /progress/due` becomes the actual "what should I study next" endpoint — the thing that makes the system adaptive rather than just retrieval + quiz.

**Definition of done:** answering questions across a few sessions visibly changes `next_review_at` and which topics `GET /progress/due` surfaces — this is the part worth demoing.

## Where you are right now

Phases 0, 1, 2, and 3 are done. The current ingestion flow accepts `.txt` uploads, stores documents under optional topics, enqueues Celery work, extracts text, chunks it, calls Hugging Face embeddings, persists vectors in Postgres through pgvector, and can retrieve relevant chunks for a topic by semantic search. Next real decision point is Phase 4: question generation.
